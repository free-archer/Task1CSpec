# Task1CSpec

Task1CSpec - оркестратор спецификаций задач 1С для Codex. Он хранит спецификации в `ProjectSpecs`, ведет работу по фиксированным ролям и архивирует папки завершенных задач.

## Структура каталогов

Все спецификации должны храниться внутри:

```text
ProjectSpecs/
  Архив/
  Документация/
  Задачи в работе/
```

Папки задач создаются в `ProjectSpecs/Задачи в работе/`. Завершенные задачи переносятся в `ProjectSpecs/Архив/`. Проектная документация хранится в `ProjectSpecs/Документация/`.

## Идентификация задачи

Если задача не передана, `/TaskStart` должен запросить ее в точном пользовательском формате:

```text
RTD-2343: Доработка переключения вызова из ОМ ВнешниеДанные. ТоварныеОперации
```

Номер задачи - часть строки до первого двоеточия. Перед созданием новой папки обязательно найди существующую папку по этому номеру. Если папка не найдена, сообщи об этом пользователю и спроси, новая ли это задача. Создавай папку только после подтверждения.

Когда доступен `scripts/task1cspec.py`, используй его для операций `init`, `start`, `status`, `role` и `archive`. Если скрипт недоступен, выполни те же проверки вручную.

## Порядок ролей

Процесс выполняется последовательно:

| Порядок | Роль | Ролевая установка | Результат |
|---:|---|---|---|
| 1 | Аналитик | Ты аналитик 1С | `ТехЗадание.md` |
| 2 | Архитектор | Ты опытный архитектор 1С | `Архитектура.md` |
| 3 | Разработчик | Ты опытный 1С разработчик | `Реализация.md`, затем изменение кода только после утверждения |
| 4 | Тестировщик | Ты опытный 1С тестировщик владеющий навыками сценарного тестирования на vanessa-automation | `Тест-кейсы.md` |
| 5 | Технический писатель | Ты опытный технический писатель, описывающий функционал 1С программ | `Документация по задаче.md`, обновление проектной документации, архив |

На каждом этапе:

1. Прочитай все ранее созданные спецификации в папке задачи.
2. Изучи актуальное состояние проекта, важное для текущей роли.
3. Задай короткие вопросы, если для текущего этапа не хватает обязательной информации.
4. Не продолжай этап, пока пользователь не ответит на обязательные вопросы.
5. Создавай или обновляй только результат текущей роли, если этап явно не требует изменения кода или проектной документации.
6. После создания результата остановись и передай файл пользователю на проверку.

## Инструкции по этапам

### Аналитик

Создай `ТехЗадание.md`.

Спецификация должна включать:

- цель задачи в понятной и проверяемой формулировке
- `Как сейчас`
- `Как должно быть`
- `Как проверить результат`

`Как проверить результат` - это не список формальных тест-кейсов, а описание того, как заказчик может убедиться, что цель задачи достигнута.

### Архитектор

Создай `Архитектура.md`.

Перед написанием:

- изучи доступную кодовую базу и метаданные 1С в репозитории
- задействуй все релевантные доступные MCP-серверы
- используй все доступные правила и скилы по стандартам разработки 1С и правилам именования объектов 1С

Спецификация должна быть краткой и описывать:

- какие объекты 1С создаются
- какие объекты 1С изменяются
- какие объекты 1С удаляются
- названия новых объектов 1С
- названия новых функций и процедур
- точные программные модули, где будет расположен новый код

Не добавляй в этот файл подробные алгоритмы и логику реализации.

### Разработчик

Создай `Реализация.md`.

Спецификация должна описывать программную реализацию и включать основные функции, процедуры, алгоритмы и показательные фрагменты кода 1С, необходимые для проверки решения.

Менять программный код можно только следующим шагом после проверки и явного утверждения `Реализация.md`. До этого утверждения код не изменяй.

### Тестировщик

Создай `Тест-кейсы.md`.

Спецификация должна включать:

- ручные тест-кейсы для тестировщиков
- Gherkin-сценарии, пригодные для сценарной автоматизации в стиле Vanessa Automation
- предусловия, тестовые данные, шаги, ожидаемые результаты, негативные и регрессионные проверки, если они применимы

### Технический писатель

Создай `Документация по задаче.md`.

Документ должен описывать задачу для проектной документации без избыточных технических деталей:

- что изменено
- зачем это изменено
- как работает результат
- как задача проверялась
- какой результат достигнут

После проверки пользователем:

1. Обнови или создай релевантные доменные файлы документации в `ProjectSpecs/Документация/`.
2. Отдельно спроси пользователя, переносить ли папку задачи в `ProjectSpecs/Архив/`.
3. Перенеси папку задачи только после явного подтверждения.

## Шаблоны

Используй `references/templates.md` как обязательную структуру разделов. Шаблоны можно адаптировать под задачу, но обязательные разделы и имена файлов должны остаться неизменными.

## Проверки завершения

Перед сообщением о завершении этапа Task1CSpec проверь:

- целевая папка задачи находится в `ProjectSpecs/Задачи в работе/`, если явное действие не было архивацией
- все спецификации предыдущих этапов существуют или пользователь намеренно запустил роль вне очереди
- файл результата имеет точное требуемое имя
- файл результата содержит обязательные разделы своего этапа
- на финальном этапе проектная документация обновлена до архивации
- архивация подтверждена отдельно, а папка задачи находится в `ProjectSpecs/Архив/`
